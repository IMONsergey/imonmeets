# Комнаты, квота и модерация

## Единица тарифа и история

Лимит `rooms` означает число **открытых** комнат пространства. Закрытие освобождает место под новую комнату. Закрытую комнату нельзя снова открыть: для нового звонка создается новая комната с новой ссылкой. Это сохраняет границу доступа старой встречи.

Архив — обратимое перемещение закрытой комнаты из списка завершенных. Он сохраняет историю чата, записи, сроки хранения и права участников пространства. Возврат из архива не открывает комнату и не расходует квоту. Ни архив, ни закрытие не обещают бессрочного хранения: отдельные retention policies продолжают действовать.

Список комнат использует страницы по 100 записей и cursor по паре `created_at,id`. Параметры `view=open|closed|archived|all`, `q` и `before` фильтруются сервером в границах текущего пространства. В тарифе возвращается `roomsQuotaBasis: open`.

## Ограничения запросов

Общий IP служит грубой защитой от потока запросов, а не идентификатором участника. Установлены отдельные shared PostgreSQL budgets:

| Категория                                     | Лимит за минуту |
| --------------------------------------------- | --------------: |
| Общие API-запросы одного IP / IPv6 /64        |            6000 |
| Запросы входа в комнату одного IP             |             600 |
| Проверенный аккаунт                           |             300 |
| Вход конкретного аккаунта / browser guest key |              20 |
| Чтение чата по проверенному room session      |             120 |
| Чтение состояния проверенного waiting ticket  |              60 |
| Отправка сообщений                            |              30 |

Auth endpoints имеют отдельную политику. Все лимиты являются предохранителями; пропускная способность звонков требует отдельного нагрузочного приема.

Чат не опрашивается при закрытой панели или скрытой вкладке. Открытие и возврат вкладки догружают историю. Ошибки вызывают backoff, учитывается `Retry-After`; отозванный/закрытый сеанс не опрашивается бесконечно.

## Self-hosted LiveKit: обязательная граница

На используемую операцию `RemoveParticipant` нельзя возлагать отзыв ранее выданного JWT. Официальная документация различает LiveKit Cloud и self-hosted: https://docs.livekit.io/frontends/reference/tokens-grants/ .

Поэтому точечная модерация включается только за защищенным signaling ingress:

1. Публичные handshake/reconnect и validation проходят серверный admission check на всех четырех exact routes: `/rtc`, `/rtc/validate`, `/rtc/v1`, `/rtc/v1/validate`. Установленный livekit-client 2.23.0 предпочитает v1 и сохраняет `access_token` в query; legacy используется как fallback.
2. Прямой публичный доступ к signaling-порту LiveKit отсутствует. Внутренние Egress и server SDK используют приватный адрес.
3. Nginx subrequest делает GET `/api/internal/livekit/authorize` с отдельным секретом `X-IMON-LiveKit-Auth` и JWT в `Authorization: Bearer …` либо `X-IMON-LiveKit-Token`. JWT не передается в query API и не журналируется.
4. При включенном общем origin proxy guard также передаются его секрет и доверенный client IP. Новый секрет не заменяет существующую границу.
5. Endpoint проверяет подпись, issuer, expiry, exact identity и room; затем текущий статус комнаты, generation, живой grant, отзыв, бан и удаление из пространства. Ответы без данных: 204 разрешено; 401 неверный JWT; 403 доступ запрещен; 503 неизвестное состояние/ошибка БД/отключенный gate.
6. Нет fallback «пропустить при ошибке». Nginx должен закрыть доступ при любом ответе, кроме успешного.
7. Для включения нужны `LIVEKIT_SIGNALING_AUTH_ENABLED=true` и `LIVEKIT_SIGNALING_AUTH_SECRET` длиной минимум 32 символа. Сам флаг не доказывает правильность ingress: требуется реальная приемка.

### Удалить и заблокировать

«Удалить» отзывает выбранный live session и disconnect-ит его. Участник может запросить новый вход, старые media/chat credentials остаются недействительными.

«Заблокировать» отзывает все сеансы того же аккаунта или известного browser guest key в данной комнате и запрещает выдачу нового grant. Already-admitted waiting tickets этого субъекта также закрываются. Отмена блокировки разрешает новый вход, но не оживляет старые токены.

Анонимного человека нельзя надежно распознать после удаления cookies или смены браузера. Поэтому после любого бана **все новые гости** проходят зал ожидания. Это также не позволяет заблокированному участнику выйти из аккаунта и незаметно вернуться как новый гость. Решение организатора допустить новую неизвестную личность остается отдельным действием. Существующие невиновные участники не меняют room generation и не отключаются.

Организатор не удаляет сам себя этой операцией; используются обычные controls выхода. Владелец защищен. Удалять администратора может только владелец; обычный участник управляет модерацией только в созданной им комнате и не может удалять администраторов/владельца.

Историческая privacy-модель остается workspace-wide: участники команды имеют доступ к истории комнаты в пространстве. Бан live-сеанса не превращает историю в приватный ACL.

### Неопределенное внешнее действие

Отзыв grants и запись задания на отключение коммитятся **до** внешнего LiveKit RPC. Неопределенный RPC не откатывает отзыв и не выдается за успешное отключение: API возвращает `PARTICIPANT_DISCONNECT_PENDING`, durable очередь повторяет действие.

Задания имеют revision, чтобы завершающийся старый RPC не удалил новое задание, созданное конкурентным событием. Подписанный `participant_joined` повторно проверяет состояние: handshake, разрешенный перед конкурентным баном и завершившийся позже, также отключается. Дубликат события не отменяет эту проверку. Внешний webhook не заменяет ingress check.

## Обязательная реальная приемка перед включением

DB/integration tests проверяют настоящие PostgreSQL locks, counters, schema migrations и подписанные JWT; LiveKit RPC в них моделируются. Они не являются доказательством media ingress.

В отдельном окружении с точным self-hosted LiveKit образом и новым ingress необходимо проверить:

- Два обычных участника и организатор; удаление/бан одного не разрывают звонок остальных.
- Replay исходного и обновленного LiveKit JWT после бана, включая `/rtc`, `/rtc/validate` и reconnect.
- Прямой signaling-порт, альтернативные hostname/path и публичные server API не обходят gate.
- Задержанный handshake, конкурирующий с баном, вызывает signed-event enforcement.
- Остановка API/БД закрывает новые signaling connections; уже установленный звонок и восстановление имеют согласованное поведение.
- Ошибка RemoveParticipant дает pending state, повтор безопасен, после восстановления внешнего сервиса заданий не остается.
- Egress/internal service participants не попадают под guest/member cleanup.
- Реальные browser/SDK guest sessions и iframe; отсутствие cookies приводит к admission, а не к молчаливому обходу.

Без этой проверки функция в production остается выключенной.
