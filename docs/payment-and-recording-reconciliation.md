# Сверка неопределенных операций

Сверка изменяет только сохраненный заказ или резервирование записи после независимого запроса состояния к тому же провайдеру. Она не создает оплату, возврат, новую запись и не снимает резервирование на основании отсутствия ответа.

## Платежи и возвраты

Фоновый обработчик раз в минуту выделяет отдельные слоты для ожидающих оплат и успешных оплат. В PostgreSQL фиксируются трехминутная аренда проверки, следующая попытка, число ошибок и безопасный код ошибки. Это защищает от одновременной обработки одной записи несколькими API и от вытеснения сверки возвратов ожидающими заказами. За цикл обрабатываются максимум четыре ожидающих и четыре успешных заказа; один запрос к YooKassa ограничен десятью секундами. Все GET к провайдеру проходят общий бюджет 60 в минуту.

Успешные оплаты проверяются раз в шесть часов, пока не подтвержден полный возврат. Потерянный webhook возврата восстанавливается canonical GET. При росте очереди оператор должен следить за возрастом просроченного next_check_at; интервал проверки не является обещанием максимальной задержки при исчерпании пропускной способности. Ошибки используют ограниченную экспоненциальную задержку.

refunded_kopecks хранит подтвержденную сумму возврата в копейках и никогда не уменьшается от устаревшего ответа. Частичный возврат сохраняет оставшийся оплаченный период без автоматического пропорционального пересчета; интерфейс показывает сумму возврата. Полный возврат однократно отменяет только неиспользованную часть соответствующего заказа. Отдельные поздние продления сохраняются.

При неопределенном создании используется тот же сохраненный Idempotence-Key только первые 20 часов, внутри документированного YooKassa окна 24 часа. После этого новый POST запрещен, заказ блокирует повторную оплату. Оператор находит существующий provider payment ID в кабинете/поддержке YooKassa. API делает GET и проверяет точный ID ответа, аккаунт магазина, test mode, сумму/валюту и metadata с локальным paymentId/workspaceId/userId/planId. Локальный paymentId является ключом идемпотентности создания; API не утверждает, что GET возвращает сам заголовок Idempotence-Key.

## Доступ и двухэтапная сверка

Только текущий владелец пространства может выполнить preview/apply через свою штатную сессию. Роль перепроверяется под блокировкой пространства после внешнего GET. Лимиты каждого типа сверки: 12 запросов в час на пользователя, 24 на пространство, 60 в минуту глобально. Провайдерские ключи, cookies и сырые ответы не попадают в журнал сверки.

Preview возвращает текущее и подтвержденное состояние, auditId и SHA-256 version. Apply требует previewAuditId и version того же владельца, заказа/записи и пространства. Предварительная сверка действует 15 минут. API заново получает состояние провайдера; любое изменение значимых данных требует нового preview. Изменение локальных данных и запись аудита выполняются в одной транзакции. В im_audit сохраняется reconciliation_version, а не внешний ответ или секреты.

CLI использует IMON_OWNER_COOKIE из защищенного окружения. Не передавайте cookie в argv, не сохраняйте его в shell history и не публикуйте. Не используйте серверный master-secret.

Предварительная сверка:

    node scripts/reconcile-operation.mjs --origin https://meets.example.com --workspace WORKSPACE_ID --kind payment --local-id LOCAL_PAYMENT_UUID --provider-id PROVIDER_PAYMENT_UUID

После просмотра конкретного результата:

    node scripts/reconcile-operation.mjs --origin https://meets.example.com --workspace WORKSPACE_ID --kind payment --local-id LOCAL_PAYMENT_UUID --provider-id PROVIDER_PAYMENT_UUID --apply --preview-audit-id AUDIT_ID --version VERSION_SHA256

Для записи используйте --kind recording и provider ID вида EG_.... API routes: POST /api/workspaces/:workspaceId/payments/:paymentId/reconcile и POST /api/workspaces/:workspaceId/recordings/:recordingId/reconcile. Техническая форма с provider IDs в пользовательский интерфейс не добавляется.

## Записи

Сверка выполняет ListEgress с точным egressId. Сопоставляются сохраненные при старте media_name (включая поколение), object_key и уже известный egress_id. Текущее поколение комнаты не подменяет поколение записи. При отсутствии сохраненного media_name, несовпадении, пустом/неоднозначном ответе или ошибке резервирование сохраняется. Legacy-запись без доказанного поколения требует анализа исторических журналов.

Только подтвержденный результат Egress меняет состояние. Завершение с ожидаемым файлом переводит запись в complete; подтвержденные FAILED/ABORTED и правила LIMIT_REACHED обрабатываются общей машиной состояний записей. Наличие метаданных Egress не заменяет проверку доступности/целостности файла в объектном хранилище. Сверка не перезапускает запись и не выдает новый доступ к файлу.

## Неопределенный исход без provider ID

Пустой список, 404, тайм-аут и истечение времени не доказывают, что операция не произошла. Автоматического force-fail/force-release нет. Сохраняйте локальный ID, время, ожидаемый media_name/object_key или платежные metadata и обращайтесь к провайдеру/проверяйте его журналы. Получив положительно подтвержденный ID, повторите preview. Если ID и достоверного результата получить невозможно, резервирование и запрет повторного заказа остаются; это явно ограниченный аварийный случай, а не «успешное восстановление».
