В ICE-статистике присутствует `relayProtocol: "tls"`.
`decodedFramesPerSecond` в файле суммируется по получаемым видеопотокам клиента;

определяет максимальную вместимость сервера. Не измерены длительные звонки,
несколько одновременных комнат, запись под нагрузкой, реальные мобильные
устройства, Safari на iOS и сети конкретных заказчиков. Значение лимита в
конфигурации не заменяет такие измерения.

Для сетей, допускающих только TCP 443, отдельный медиавход еще нужен. Существующий
VPN занимает этот порт; его конфигурация не менялась. Работа TURN TLS на 5349
не подтверждает совместимость с ограничением только на 443.

## Копии, мониторинг и восстановление

Автоматический перенос больше не зависит от проблемного SSH-соединения Mac с
сервером. Он использует существующий HTTPS-вход 8443, read-only bearer и системный
curl с проверкой сертификата и имени хоста. Передаются только зашифрованный
архив и сокращенный статус проверок. Приватный ключ расшифровки хранится на Mac.

## Запись и ресурсы общего сервера

Отдельный loop-образ имеет точный размер **1 GiB**. После монтирования измеренная
емкость ext4 составляет **1 020 702 720 байт**. При отсутствии mount исходная
директория имеет права `000`; непривилегированный процесс хранилища не должен
писать вместо нее в общую файловую систему. Installer и контейнер проверяют
предел емкости. Посторонние контейнеры и VPN не перенастраивались.

Для первоначального режима подготовлены следующие ограничения:

| Параметр             | Значение и смысл                                                                    |
| -------------------- | ----------------------------------------------------------------------------------- |
| Одновременная запись | 1 на приложение                                                                     |
| Профиль              | MP4, 1280 × 720, 15 кадров/с                                                        |
| Остановка worker     | 30 минут или порог 350 MiB; финальная сборка файла может добавить небольшой объем   |
| Egress               | 2 CPU и 4 GiB RAM                                                                   |
| Хранение             | 3 дня с отказом доступа после истечения и повторными попытками физического удаления |
| Общая емкость S3     | 1 GiB вместе с метаданными и служебными операциями                                  |

Сбой Chrome sandbox с `chroot` исправлен. Реальный браузерный сценарий с двумя
участниками прошел цикл «начать, остановить, скачать приватный MP4, физически
удалить» с настоящими Egress и S3. Тест завершился успешно примерно за
1,5 минуты; полный запуск проверок занял 116,02 секунды. Использовались отдельная
тестовая база и временные учетные данные приложения/почты, которые после проверки
удалены. Сценарий: [recording.spec.ts](../tests/e2e/recording.spec.ts).

### Найденный и исправленный дефект manifest

Финальная инвентаризация хранилища выявила два оставшихся JSON manifest Egress
по 438 байт от изолированной и рабочей тестовых записей. Сами MP4 уже были
удалены и доступ к ним прекращен, но служебные файлы оставались в bucket.
Первый успешный тест скачивания и удаления MP4 поэтому не подтверждал полную
очистку всех связанных объектов.

В окончательном выпуске `5880571` новый Egress output явно использует
`disableManifest:true`. Удаление записи также удаляет точный связанный manifest
старого формата; произвольные префиксы и чужие объекты не затрагиваются.
Ошибка удаления manifest сохраняет незавершенное состояние очистки для
повторной попытки. Это поведение проверено в API-тестах.
Два известных служебных объекта от проверочных записей удалены адресно.
